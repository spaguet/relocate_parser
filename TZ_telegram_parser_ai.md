# ТЗ: ИИ-помощник для путешественников и экспатов

> Рабочее название репозитория — `relocate_helper`. Документ описывает не только парсер Telegram, но и полный контур: сбор данных, базу знаний, модерацию, платного бота и административную панель.

## 1. Цель продукта

Создать платного Telegram-бота, который отвечает на практические вопросы путешественников и экспатов по конкретным странам и городам на основе собственной базы знаний.

Примеры вопросов:

- «Сколько стоит маникюр в Рио-де-Жанейро?»
- «Где оформить CPF и какие документы нужны?»
- «В каком районе лучше жить с ребёнком?»
- «Какие русскоязычные стоматологи есть в городе?»

База знаний формируется из разрешённых источников:

- публичных Telegram-групп и каналов;
- доступных владельцу проекта Telegram-чатов;
- форумов и открытых веб-страниц;
- переданных вручную текстов и файлов;
- транскриптов YouTube-видео, подготовленных через NotebookLM;
- других источников, добавленных позднее.

Система запускается поэтапно: сначала один город (или одна страна), после проверки качества — следующие географии. Архитектура с первого дня должна допускать несколько городов через справочники, но продуктово MVP ограничен одной географией.

### 1.1 Термины

| Термин | Значение |
|---|---|
| Документ (`documents`) | Исходный материал целиком: сообщение, страница, файл, транскрипт |
| Фрагмент (`chunks`) | Смысловой кусок документа для поиска и доказательств |
| Факт (`facts`) | Структурированное извлечённое знание с метаданными |
| Карточка (`knowledge_cards`) | Агрегированная сводка по географии + теме/подтеме |
| Доказательство | Связь факта с одним или несколькими фрагментами (`fact_evidence`) |
| Успешный ответ | Запрос, для которого началась генерация финального ответа дорогой моделью (см. раздел 7.1) |
| Порог публикации | Когда извлечённый факт можно автоматически перевести в `published` |
| Порог достаточности ответа | Когда найденных материалов хватает, чтобы сформировать ответ пользователю (может быть ниже порога публикации) |
| Tombstone | Служебная запись о том, что исходный документ удалён/обезличен и больше не должен участвовать в поиске и генерации |

## 2. Важные архитектурные решения

### 2.1 Двухуровневая база знаний, а не «вопрос → SQL»

Обычная реляционная база и преобразование вопроса в SQL недостаточны. Пользователи формулируют один и тот же вопрос разными словами, а нужные сведения часто находятся внутри длинных сообщений и обсуждений.

Нужна двухуровневая модель:

1. **Структурированная база знаний** — извлечённые факты, цены, организации, инструкции, адреса, темы, география, даты и ссылки на подтверждения; плюс агрегированные **карточки знаний** по темам.
2. **Индекс исходных материалов** — очищенные фрагменты сообщений, страниц и транскриптов для семантического и полнотекстового поиска.

Основной ответ строится по опубликованным структурированным данным. Порядок retrieval: **карточки → факты → исходные фрагменты (RAG)**. Если структурированных данных недостаточно, система ищет подтверждения в исходных фрагментах. Ответ генерируется только на найденных материалах; при недостатке данных — честный отказ.

SQLite допустим только для одноразового прототипа парсера. Для мультигородской базы, параллельной обработки и платного бота нужен PostgreSQL (см. раздел 8).

### 2.2 ИИ не публикует знания бесконтрольно

ИИ автоматизирует классификацию, извлечение фактов, объединение дублей и подготовку сводок, но может ошибаться. Поэтому нужны:

- ссылки каждого факта на исходные фрагменты;
- оценка уверенности по единой шкале `0.0–1.0`;
- дата или период актуальности;
- обнаружение противоречий;
- автоматические проверки формата и диапазонов (валюта, цена > 0, известный город и т.п.);
- статусы записи: `draft` → `needs_review` → `published` / `rejected` / `hidden`;
- ручная модерация спорных или важных данных через административную панель.

**Жизненный цикл статусов:**

- все извлечённые записи создаются в `draft`;
- при выполнении правил ниже и прохождении автопроверок запись переводится в `published` без ручного шага;
- при недостатке подтверждений, низкой уверенности или конфликте — в `needs_review`;
- если опубликованный факт потерял доказательства, стал противоречивым, устарел по правилу свежести или исходный материал был удалён/изменён, факт автоматически понижается как минимум до `needs_review` с пересчётом зависимых карточек;
- администратор может перевести запись в `published`, `rejected` или `hidden`.

Пороги **публикации** настраиваются администратором. Числовые значения уверенности и достаточности для **ответа пользователю** задаются отдельно (раздел 15, пункт 12). Стартовые правила MVP:

| Тип сведений | Автопубликация | Минимум подтверждений | Примечание |
|---|---|---|---|
| Бытовые цены и услуги | да, при пороге уверенности из раздела 15 | ≥ 2 независимых источника | иначе `needs_review`; в ответе допустимо «единичное упоминание», если порог достаточности ответа ниже порога публикации |
| Адреса и контакты организаций | да, если данные публичны | ≥ 1 | только явно опубликованные контакты бизнеса |
| Юридические, миграционные, медицинские, финансовые | нет | ручная модерация | в ответе — предупреждение проверить в официальном источнике |

«Независимый источник» = разные записи в `sources`, а не разные сообщения одного чата.

### 2.3 Разделить сбор данных и пользовательского бота

Независимые сервисы:

1. **Сборщики данных** — материалы из источников.
2. **Конвейер обработки** — очистка, индексация, извлечение знаний.
3. **База знаний** — факты, карточки и исходные фрагменты.
4. **Telegram-бот** — вопросы и ответы.
5. **Административная панель** — источники, обработка, качество, подписки.

Сбой парсера или очереди импорта не должен останавливать пользовательского бота.

## 3. Пользовательские роли

### 3.1 Пользователь

- запускает Telegram-бота;
- в MVP работает в контексте одного города по умолчанию; выбор страны/города включается при появлении второй географии;
- задаёт вопрос на естественном языке;
- получает краткий ответ с датой (или периодом) актуальности и названиями/ссылками источников — в объёме, согласованном в разделе 15, пункт 5;
- при необходимости раскрывает подробности (follow-up в том же диалоге);
- покупает доступ на 1 / 7 / 30 дней (продление — повторная покупка, не автопродление, если иное не решено в разделе 15);
- видит срок действия доступа и может продлить его;
- оценивает ответ или сообщает об ошибке.

### 3.2 Администратор

- добавляет страну, город и источники;
- запускает первичную и повторную синхронизацию;
- загружает тексты, документы и транскрипты;
- наблюдает статус и ошибки обработки;
- просматривает извлечённые факты, карточки и доказательства;
- исправляет, подтверждает, скрывает и объединяет записи;
- управляет темами, географическими тегами, синонимами и стоп-листом;
- настраивает пороги публикации, лимиты тарифов и внутренние бюджеты LLM;
- просматривает обезличенную статистику запросов и расхода токенов;
- управляет тарифами, промокодами и доступом пользователей.

## 4. Источники и способы загрузки

### 4.1 Telegram

Для чтения истории групп нужен Telegram Client API и пользовательская сессия (например, Telethon). Обычный Bot API не позволяет произвольно скачивать старую историю чужих групп.

Сборщик должен:

- принимать ссылку, username или ID группы/канала;
- загружать сообщения за заданный период;
- сохранять текст, дату, связь reply/thread, реакции и метаданные медиа (без обязательного скачивания бинарных файлов в MVP);
- докачивать только новые или изменённые сообщения (по `message_id` + `edit_date`);
- обрабатывать удаление сообщений в источнике: помечать документ/фрагмент как удалённый в источнике, снимать или понижать статус зависимых фактов и пересчитывать карточки;
- корректно переживать `FloodWait`;
- поддерживать удаление или обезличивание по запросу субъекта данных (право на удаление);
- не публиковать личные контакты частных лиц из обсуждений; публичные контакты допускаются только для организаций или специалистов, которые явно разместили их как контакт для клиентов;
- хранить `source_id` и идентификатор исходного сообщения для внутренней трассировки.

По возможности используются публичные источники без доступа к личному аккаунту. Если авторизация необходима, её выполняет владелец проекта. Пароли, коды подтверждения и файл сессии нельзя передавать ИИ-ассистентам разработки и нельзя хранить в репозитории.

### 4.2 Форумы и веб-страницы

Приоритет способов получения:

1. официальный API или RSS;
2. разрешённый экспорт;
3. загрузка текста/HTML администратором;
4. аккуратный краулер открытых страниц с соблюдением правил сайта и ограничений частоты.

Для каждой страницы сохраняются URL, заголовок, дата публикации или обновления (если есть), дата загрузки и доступный автор.

### 4.3 Facebook и закрытые площадки

Только официальный API, разрешённый экспорт или ручная загрузка. Автоматический обход ограничений, CAPTCHA и закрытых разделов не входит в проект. Доступ к личному аккаунту — только при явной необходимости и после оценки правил площадки и рисков блокировки.

### 4.4 YouTube

Администратор транскрибирует видео (например, через NotebookLM) и загружает текст вместе с:

- ссылкой на видео;
- названием канала и видео;
- датой публикации;
- языком;
- таймкодами, если доступны;
- страной и городом;
- темами, заданными администратором.

Автоматическое получение субтитров через API — вне MVP (раздел 14).

### 4.5 Ручная загрузка

Форматы MVP: TXT, Markdown, CSV, JSON и PDF с извлекаемым текстом (без OCR в первой версии). Для каждого файла администратор указывает источник, географию, язык, дату актуальности и правовое основание использования.

## 5. Конвейер обработки данных

### 5.1 Этапы

1. Сохранить исходный документ в объектном хранилище в версии, пригодной для аудита и переобработки, но с учётом сроков хранения и правовых требований на удаление/обезличивание.
2. Нормализовать кодировку, разметку, ссылки, даты и пробелы.
3. Определить язык. При необходимости подготовить **поисковый** перевод или мультиязычные embeddings; язык ответа пользователю — язык вопроса (если поддерживается в MVP), а не язык исходника.
4. Удалить дубли, спам и технические сообщения.
5. Обезличить лишние персональные данные участников, **не удаляя** публичные контакты организаций и специалистов, явно опубликованные для клиентов.
6. Разбить длинный материал на смысловые фрагменты с небольшим пересечением.
7. Определить страну, город, район и темы.
8. Извлечь структурированные факты.
9. Создать полнотекстовый индекс и векторные представления фрагментов.
10. Связать каждый факт с одним или несколькими фрагментами-доказательствами.
11. Рассчитать уверенность, свежесть и статус публикации по правилам раздела 2.2.
12. Обновить или пересобрать агрегированные карточки знаний по затронутым темам и географии.
13. При пометке документа как удалённого или изменённого в источнике — инвалидировать зависимые факты, доказательства и карточки (согласовано с разделом 4.1).

Все этапы повторяемы и версионируемы: смена модели или промпта не требует повторного скачивания источников. Переобработка идёт от сохранённого исходника или нормализованной версии.

### 5.2 Какие данные извлекать

- страна, город, район;
- тема и подтема;
- организация или место;
- услуга или товар;
- цена, валюта, единица измерения и диапазон;
- дата или период, к которому относится информация;
- адрес, контакты и график работы — только если они опубликованы для бизнеса/специалиста;
- краткая рекомендация или инструкция;
- тональность оценки (положительная / отрицательная / нейтральная), если явно выражена;
- ограничения и условия;
- язык исходника;
- ID доказательств;
- уровень уверенности `0.0–1.0`.

Цены разных вариантов услуги не смешиваются. Пример: обычный маникюр, маникюр с покрытием и снятие покрытия — отдельные сущности/подтемы, даже если в быту их называют одним словом.

### 5.3 Темы

Начальный справочник (конкретные 5–7 для MVP выбираются в разделе 15, пункт 3):

- документы, визы и легализация;
- жильё и районы;
- транспорт;
- медицина и страхование;
- красота и бытовые услуги;
- банки, платежи и обмен валют;
- мобильная связь и интернет;
- образование и дети;
- покупки и доставка;
- рестораны и продукты;
- работа и бизнес;
- безопасность;
- досуг и сообщества.

Темы и подтемы расширяются через справочник без миграции схемы «под каждую новую тему».

### 5.4 География и теги

Каждый документ, фрагмент и факт может иметь:

- страну;
- регион/штат;
- город;
- район;
- несколько тематических тегов;
- язык;
- период актуальности.

Географические сущности хранятся в справочнике с альтернативными названиями, например: `Rio de Janeiro`, `Рио-де-Жанейро`, `Рио`.

### 5.5 Карточки знаний

`knowledge_cards` — агрегированные сводки по паре «география + тема/подтема» (и при необходимости сущности вроде услуги). Карточка обновляется при появлении новых опубликованных фактов и хранит:

- краткий итог;
- число наблюдений;
- диапазон/медиану для цен, если применимо;
- период данных;
- ссылки на факты-основания;
- статус публикации и дату пересчёта.

В retrieval карточки имеют приоритет над отдельными фактами; сырые факты — над исходными `chunks`; `chunks` используются как запасной контур.

## 6. Логика ответа пользователю

### 6.1 Обработка вопроса

1. Проверить активный доступ и лимиты (раздел 7).
2. Определить язык, географию, тему, сущности и временной контекст (дешёвая модель или правила). Этот шаг относится к внутреннему бюджету LLM и **не** считается успешным ответом для пользовательского лимита.
3. Если город критичен для ответа, но не задан и не выведен однозначно — уточнить, не угадывать.
4. Выполнить гибридный поиск: полнотекстовый + семантический, с фильтрами по географии, теме и свежести; учесть синонимы и `geo_aliases` / `topic_aliases`.
5. Сначала искать опубликованные **карточки**, затем **факты**.
6. Если их недостаточно — релевантные **фрагменты** исходных материалов.
7. Переранжировать результаты, удалить дубли, ограничить число и суммарную длину фрагментов.
8. Проверить достаточность и противоречивость доказательств по **порогу достаточности ответа** (раздел 15, пункт 12).
9. Если релевантных данных нет — ранний отказ **без** вызова дорогой модели генерации.
10. Сгенерировать ответ только на основе найденных данных; игнорировать инструкции, вложенные в загруженные тексты (защита от prompt injection).
11. Приложить дату/период актуальности и компактный список источников (формат — раздел 15, пункт 5).
12. Сохранить обезличенную диагностику поиска в `queries`; оценку пользователя — в `answer_feedback` (можно включить во второй итерации MVP, если не успевает в первую).

Внешний поиск в интернете в runtime не используется. Если когда-либо появится, ответ должен явно помечать, что он не из собственной проверенной базы.

### 6.2 Правила формирования ответа

Бот не выдумывает отсутствующие сведения. В ответе нужно разделять:

- подтверждённые факты;
- приблизительные оценки;
- мнения участников;
- сведения, которые могут быстро устареть.

Если найдено несколько цен: диапазон, медиана или типичная цена, число наблюдений и период. Нельзя выдавать «среднюю цену» по одному сообщению.

Если данные противоречат друг другу, ответ не должен «выбирать победителя» без основания. Нужны один из трёх сценариев:

- показать диапазон/варианты и явно указать период и число подтверждений;
- отдать приоритет официальному источнику, если вопрос относится к правилам, документам, медицине, финансам или другим нормативным темам;
- отказаться от уверенного вывода и предложить сверку, если противоречие нельзя снять автоматически.

Пример при достаточных данных:

> По данным 8 упоминаний за последние 6 месяцев, маникюр с покрытием в Рио-де-Жанейро обычно стоит 90–160 BRL. Медианная упомянутая цена — около 120 BRL. Стоимость зависит от района и снятия старого покрытия. Источники: обсуждения в двух локальных чатах, обновлено 20.07.2026.

Если данных мало:

> Нашёл только одно упоминание цены — 110 BRL в мае 2026 года. Этого недостаточно, чтобы назвать типичную стоимость.

Если данных нет:

> В моей базе пока нет достаточно надёжных данных по этому вопросу для Рио-де-Жанейро. Я зафиксировал запрос, чтобы базу можно было дополнить.

Для юридических, миграционных, медицинских и финансовых тем — короткое предупреждение о необходимости сверки с официальным источником.

## 7. Подписки и платежи

Тарифы первой версии:

- доступ на 1 день;
- доступ на 7 дней;
- доступ на 30 дней.

Платёжный модуль должен соответствовать актуальным правилам Telegram. Базовый вариант — Telegram Stars:

- все тарифы на старте MVP — **разовая покупка** с фиксированной датой окончания доступа;
- возобновляемая подписка Stars — только если сценарий подтверждён выбранной версией Bot API и продуктовой необходимостью (раздел 15, пункт 11).

Система хранит:

- Telegram ID пользователя;
- тариф (`plan`);
- время начала и окончания доступа в UTC;
- статус платежа;
- ID платежа провайдера;
- историю начислений и возвратов;
- использованный промокод, если есть.

Обязательные требования:

- выдавать доступ только после подтверждённого платежа;
- обрабатывать повторные webhook/уведомления идемпотентно;
- проверять доступ на каждый платный запрос;
- не хранить данные банковских карт;
- команды: «Тарифы», «Моя подписка», «Продлить», «Поддержка»;
- бесплатный пробный период — настраиваемая опция (можно выключить); длительность пробного периода задаётся в разделе 15, пункт 9;
- лимиты запросов и защита от автоматического злоупотребления.

Перед запуском проверить актуальные правила Telegram, налогообложение и обязанность выдачи чеков для выбранной юрисдикции.

### 7.1 Лимиты использования

Лимиты настраиваются per-plan без изменения кода. Стартовые значения MVP:

| Параметр | Значение |
|---|---|
| Пробный доступ | 3 успешных ответа за весь пробный период |
| Любой платный доступ | 30 успешных ответов за скользящие 24 часа |
| Частота | не более 5 запросов в минуту |
| Параллелизм | не более одного обрабатываемого запроса на пользователя |
| Длина вопроса | максимум 2 000 символов |
| Длина ответа модели | максимум 800 токенов, если сценарий не требует большего |

**Успешный ответ** — запрос, для которого началась платная обработка **финальной генерации** (дорогая модель). Не расходуют пользовательский лимит:

- команды меню и проверка подписки;
- классификация вопроса, embeddings, reranking и прочие вспомогательные вызовы LLM;
- отказ до вызова дорогой модели;
- технические ошибки до биллинга токенов генерации;
- повтор ответа из кэша (при этом активная подписка всё равно обязательна).

Если ошибка произошла после платного вызова LLM, расход токенов логируется, а пользовательский счётчик запросов по возможности откатывается.

При исчерпании скользящего лимита бот сообщает время до освобождения слота, например:

> Лимит запросов исчерпан. Следующий запрос станет доступен через 4 ч 25 мин.

### 7.2 Внутренний бюджет LLM

Скрытый от пользователя контур контроля себестоимости:

- учитывать input/output tokens, embeddings, reranking и прочие платные вызовы;
- лимит стоимости (или токенов) на пользователя за скользящие 24 часа;
- отдельный предел стоимости одного ответа;
- глобальный дневной бюджет сервиса с уведомлением администратора на 50%, 80% и 100%;
- остановка дополнительной генерации или переключение на более дешёвую модель при достижении лимита;
- журнал расхода по пользователю, модели, тарифу и типу операции;
- не показывать пользователю внутренние цены и ключи провайдеров.

Стартовый внутренний предел задаётся после замера на контрольном наборе: дневной бюджет одного пользователя не должен превышать допустимую долю цены его тарифа (конкретная доля — решение владельца, раздел 15, пункт 9).

Оптимизации стоимости:

- кэш одинаковых и семантически близких вопросов в рамках города и периода актуальности;
- дешёвая модель для классификации, дорогая — только для финального ответа;
- ограничение числа и длины фрагментов в контексте;
- ранний отказ без дорогой модели при отсутствии данных;
- возможность экстренно отключить генерацию.

Точные числа лимитов меняются администратором и не зашиваются навсегда в код тарифной логики.

## 8. Рекомендуемая техническая архитектура

### 8.1 Основной стек

- Python 3.12+;
- `aiogram` — Telegram-бот;
- `Telethon` — разрешённый импорт Telegram;
- `FastAPI` — внутреннее API; административный UI на старте — простые серверные шаблоны или лёгкий SPA (решение реализации, не блокирует ТЗ);
- PostgreSQL — основная база;
- `pgvector` — векторный поиск;
- встроенный полнотекстовый поиск PostgreSQL на старте (отдельный OpenSearch/Elasticsearch — после роста объёма);
- Redis — брокер/кэш/rate limit;
- одна очередь задач на выбор для MVP: **Dramatiq или RQ** (Celery допустим, но тяжелее для старта);
- S3-совместимое объектное хранилище для исходников;
- внешний LLM API с абстракцией провайдера;
- embeddings-модель с поддержкой языков MVP;
- Docker Compose — локальная разработка и первое развёртывание.

### 8.2 Логические модули

```text
src/
├── bot/                 # команды, диалоги, ответы, проверка подписки
├── admin/               # административное API и интерфейс
├── ingestion/
│   ├── telegram/        # импорт через Telethon
│   ├── web/             # разрешённые веб-источники
│   ├── youtube/         # импорт готовых транскриптов
│   └── files/           # ручная загрузка
├── processing/
│   ├── normalize.py
│   ├── deduplicate.py
│   ├── redact.py
│   ├── chunk.py
│   ├── classify.py
│   ├── extract_facts.py
│   ├── knowledge_cards.py
│   └── embed.py
├── retrieval/           # поиск, фильтры, reranking
├── answering/           # проверка доказательств и генерация ответа
├── billing/             # тарифы, платежи, лимиты, промокоды
├── db/                  # модели и миграции
├── workers/             # фоновые задачи
└── common/              # конфигурация, безопасность, логирование
```

### 8.3 Основные сущности базы

- `countries`, `cities`, `districts`, `geo_aliases`;
- `topics`, `topic_aliases`;
- `sources` — тип, права доступа, география, параметры синхронизации;
- `documents` — исходный материал, метаданные, версия, статус в источнике;
- `chunks` — фрагменты, полнотекстовый индекс, embedding;
- `facts` — структурированные знания, уверенность, статус публикации, период актуальности;
- `fact_evidence` — связь факта с подтверждающими `chunks`;
- `knowledge_cards` — агрегированные тематические сводки;
- `ingestion_jobs` — задания импорта/обработки и ошибки;
- `model_runs` — версии моделей, промптов и результаты прогонов;
- `users`, `plans`, `subscriptions`, `payments`, `promo_codes`;
- `usage_events` — учёт запросов, токенов и стоимости (для лимитов и аналитики);
- `answer_cache` — кэш ответов по нормализованному вопросу / семантическому ключу;
- `queries`, `answer_feedback` — обезличенная аналитика качества;
- `admin_users`, `admin_audit_log` — доступ в панель и журнал действий администраторов (отдельно от Telegram-пользователей бота).

Пользователю бота показываются агрегированные сведения и допустимые ссылки/названия источников, а не профили участников чатов. Доступ к исходным сообщениям и персональным данным — только у администраторов.

## 9. Административная панель

Минимальные экраны:

- страны, города и районы;
- источники и права на их использование;
- форма загрузки файлов и транскриптов;
- статус импорта и обработки;
- очередь ошибок;
- найденные дубли;
- факты и карточки с доказательствами и уверенностью;

- справочник тем и синонимов;
- пороги публикации и стоп-лист;

## 10. Безопасность, приватность и правовые ограничения

- Собирать только данные, на обработку которых есть законное основание и разрешение площадки.
- Не обходить технические ограничения и не собирать закрытые переписки третьих лиц.
- Минимизировать хранение usernames, телефонов, email и других персональных данных.
- Не использовать данные для профилей конкретных участников.
- Исключать персональные данные из пользовательских ответов, кроме публичных контактов организаций и специалистов, когда публикация допустима.
- Шифровать секреты и файлы сессий, ограничивать доступ, никогда не сохранять их в Git.
- Разделять development, staging и production.
- Вести аудит действий администраторов без записи секретов; полные тексты пользовательских вопросов не писать в обычные application-логи (только обезличенная диагностика и при необходимости защищённое хранилище с ограниченным доступом).
- Настроить сроки хранения исходных данных и процедуру удаления по запросу.
- Подготовить политику конфиденциальности, пользовательское соглашение и контакты для запросов на удаление.
- По авторскому праву: краткая переработанная сводка и ссылка/название источника, а не большие цитаты.
- Отдельно оценить GDPR, LGPD и законы страны владельца сервиса.

## 11. Нефункциональные требования

- Ответ на типовой вопрос: целевое p95 ≤ 10 секунд без учёта недоступности внешнего LLM.
- Фоновые задания идемпотентны и безопасны при повторном запуске.
- Импорт продолжается с последней успешной позиции.
- Документ не индексируется повторно без изменения содержимого или версии.
- Для каждого ответа можно восстановить найденные доказательства, версии модели и промпта (`model_runs` + диагностику `queries`).
- Резервное копирование PostgreSQL и объектного хранилища.
- Мониторинг: ошибки, длина очередей, стоимость LLM, время ответа, доля вопросов без данных.
- Бюджет LLM ограничивается на пользователя, запрос и день (раздел 7.2).
- Секреты — через менеджер секретов или переменные окружения.
- Целевая свежесть импорта для MVP: не реже одного успешного инкрементального прогона по активным Telegram-источникам в сутки (точное расписание — настраиваемое).
- Удалённые или обезличенные документы не участвуют в retrieval; вместо полного исходника может оставаться только минимальный audit/tombstone без пользовательского содержимого.

## 12. MVP: первый город

Рекомендуемый объём:

1. Один город и одна основная языковая пара «вопросы ↔ источники» (допускается второй язык источников, если он критичен для города).
2. 3–5 Telegram-источников, несколько текстов/форумов и 5–10 транскриптов.
3. 5–7 наиболее востребованных тем из справочника (раздел 5.3).
4. Импорт, очистка, дедупликация и географические теги.
5. Извлечение фактов с доказательствами и базовые карточки знаний.
6. Гибридный поиск по карточкам/фактам и исходным фрагментам.
7. Telegram-бот с ответом, источниками и сбором обратной связи.
8. Простая административная панель модерации.
9. Доступ на 1 / 7 / 30 дней + настраиваемый пробный период.
10. Набор из 100–200 контрольных вопросов для оценки качества.

Критерии готовности MVP:

- не менее 80% контрольных вопросов: retrieval находит релевантные материалы **или** бот корректно отказывает без галлюцинаций;
- каждый содержательный ответ имеет хотя бы одно доступное внутреннее доказательство;
- цены и другие изменяемые данные сопровождаются датой или периодом;
- сведения одного города не попадают в ответ о другом;
- бот не выдаёт персональные данные участников;
- платный доступ корректно начинается и заканчивается;
- лимиты (раздел 7.1) соблюдаются;
- администратор видит вопросы, по которым данных не хватило.

## 13. Этапы разработки

### Этап 0. Уточнение продукта

- выбрать первый город, языки и начальные темы;
- определить разрешённые источники и правовое основание;
- выбрать юрисдикцию бизнеса и способ оплаты;
- подготовить контрольные вопросы и эталонные ожидания;
- зафиксировать ответы на открытые решения (раздел 15).

### Этап 1. Хранилище и импорт

- развернуть PostgreSQL, pgvector и объектное хранилище;
- реализовать справочники географии, тем и источников;
- реализовать Telegram-импорт и ручную загрузку;
- добавить идемпотентность, версии и журнал ошибок.

### Этап 2. Обработка знаний

- очистка, обезличивание и дедупликация;
- разбиение на фрагменты;
- классификация по географии и темам;
- извлечение фактов, карточки знаний и embeddings;
- административная проверка и статусы публикации.

### Этап 3. Поиск и ответы

- гибридный retrieval;
- reranking и пороги достаточности;
- генерация ответа с источниками и датами;
- защита от галлюцинаций и prompt injection;
- оценка на контрольном наборе;
- кэш ответов и ранний отказ.

### Этап 4. Пользовательский бот и платежи

- onboarding (для MVP — фиксация города по умолчанию);
- команды вопросов и обратной связи;
- тарифы, оплата, продление и проверка доступа;
- лимиты, внутренний бюджет LLM, поддержка и продуктовая аналитика.

### Этап 5. Эксплуатация и масштабирование

- мониторинг и резервные копии;
- контроль стоимости;
- расписание обновления источников;
- добавление следующего города через справочники и конвейер;
- улучшение качества по вопросам без ответа.

## 14. Что не входит в первую версию

- автоматический сбор закрытых чатов без разрешения;
- обход CAPTCHA, платных стен и блокировок площадок;
- автоматическая транскрибация YouTube и OCR для сканов PDF;

- мобильное приложение и голосовой интерфейс;
- персональные рекомендации на основе профилирования участников;
- полноценный multi-city UX (выбор города) — до появления второй географии;
- возобновляемые подписки Stars — до подтверждения поддержки и продуктовой необходимости;
- гарантии юридической, медицинской или финансовой точности.

## 15. Открытые решения перед началом реализации

Нужно определить:

1. Первый город и страну.
2. Языки вопросов и источников.
3. Первые 5–7 тем.
4. Список источников и законное основание для их использования.
5. Показывать ли пользователю кликабельные ссылки на исходники или только названия источников.
6. Ожидаемый объём сообщений и документов в первом городе.
7. Срок хранения исходных материалов и срок хранения логов запросов.
8. LLM-провайдер, embeddings-модель и допустимый месячный бюджет.
9. Цены тарифов, длительность и лимиты пробного периода, а также доля тарифа как потолок себестоимости ответа/дня.
10. Юрисдикцию владельца сервиса и требования к платежам/чекам.
11. Разовая оплата Stars на 30 дней vs возобновляемая подписка.
12. Числовые пороги:
    - **публикации фактов** — минимальная уверенность и число независимых источников по типам сведений;
    - **достаточности ответа** — минимум доказательств и уверенность для генерации ответа (может быть ниже порога публикации).
13. Политика свежести по темам: через сколько дней/недель цены, контакты, правила и другие факты считаются устаревшими без нового подтверждения.
14. Способ аутентификации администраторов и политика сессий.

После этих решений ТЗ преобразуется в backlog с задачами, API-контрактами, схемой PostgreSQL и критериями приёмки для каждой функции.

## 16. Пакет промптов для реализации

Ниже приведены последовательные промпты для coding-агента. Их следует выполнять по порядку в одном репозитории. ### 16.1 Как использовать промпты
